# Boss Arena RL — контекст проекта для claude mentor

## Цель проекта
Учебный проект Ивана, состоит из двух частей:
1. **Игра на C++** (SFML): бой с одним боссом на арене. Ориентир по устройству кода — игра Zombie Arena из книги Хортона, она лежит в `~/Desktop/Zombie Arena`.
2. **RL-агент**, который учится проходить игру (убивать босса) **за минимальное время**.

## Формат работы
- Проект учебный: код пишет Иван, ментор объясняет, направляет и разбирает ошибки. Готовые решения выдавать только по прямой просьбе.
- **Документацию по ходу работы не вести.** Не нужно создавать README, design-доки, changelog и прочие отдельные файлы с описанием.
- Окружение: MacBook на Apple Silicon (arm64), работа через терминал. C++ пишется в vim, RL — на Python, GitHub — из терминала.
- C++ и SFML Иван уже применял в своих играх: Zombie Arena, Pong, Run (`~/Desktop`). RL изучает по книге Моралеса «Грокаем глубокое обучение с подкреплением».
- В Zombie Arena используется API SFML 2.x: `VideoMode(w, h)`, `event.key.code`. Перед началом нужно проверить, какая версия SFML установлена, потому что в SFML 3 API другой.

## Сроки и упрощения
- **Проект нужно сделать в сжатые сроки**, поэтому где-то задачу придётся упрощать.
- **Упрощаем игру, а не агента.** Главная ценность проекта — RL-часть: среда, награда, своя реализация алгоритма, эксперименты. Игра — только средство для неё.
- Ментор следит, чтобы работа не уходила в полировку игры (анимации, эффекты, меню, баланс «для красоты»). Когда что-то в игре можно сделать проще без вреда для RL, ментор сам предлагает упрощение.

**Что можно упростить в игре:**
- Без звуков, меню, паузы и рекордов: игра сразу стартует с боем, после конца эпизода — рестарт.
- Анимации минимальные: спрайты без кадров, вспышка босса через `boss_hit.png`, щупальце через `setTextureRect` или вообще без анимации выдвижения.
- Раскладка тёмных клеток генерируется из seed один раз на эпизод (или вообще фиксированная) и со временем не меняется.
- Атаки простые:
  - один тип снаряда, летит по прямой туда, где игрок был в момент выстрела;
  - щупальце бьёт по одной-двум колонкам после фиксированного предупреждения (`tile_warning.png`).
- У босса нет фаз; атаки по таймеру или случайно из seed.
- Коллизии — круги или AABB; движение игрока без инерции.
- Прицел можно сразу сделать дискретным (например, 16 направлений) и в ручном режиме тоже: тогда у человека и у агента одинаковое управление.
- Фиксированный размер окна или логическое разрешение 1920×1080 через `sf::View`.

**Что упрощать нельзя**, иначе пострадает RL-часть:
- `World` отдельно от рендера, методы `reset`/`step`, фиксированный dt, детерминизм по seed, headless-режим и высокая скорость симуляции;
- своя реализация RL-алгоритма и честная оценка агента (сравнение с бейзлайнами, несколько сидов).

С упрощениями на игру отводится **1 неделя** (см. «План на 5 недель»).

## Дизайн игры
- **Противник один** — большое неподвижное существо в верхней части экрана, почти во всю его ширину. У него очень много HP.
- **Атаки босса:**
  1. стреляет сгустками субстанции (снаряды);
  2. бьёт щупальцами по полю.
- **Пол** разделён на квадраты двух типов:
  - **тёмные** — периодически наносят урон, пока игрок на них стоит;
  - **светлые** — безопасные.
- **Игрок** переключается между двумя режимами (одновременно включить их нельзя):
  1. **стрельба** — патроны бесконечные;
  2. **щит** — блокирует большую часть урона.
- Подбираемых предметов нет, HP не восстанавливается.
- Игра считается пройденной, когда босс убит. Проигрыш — HP игрока на нуле.

### Что ещё не решено (обсудить, когда дойдём)
- HP босса и игрока, урон каждой атаки, какую долю урона блокирует щит.
- Есть ли задержка на переключение режима и на выстрел.
- Паттерны атак: частота, прицеливание сгустков (в игрока или с упреждением), сколько длится предупреждение перед ударом щупальцем, сколько клеток он накрывает.
- Тёмные клетки: статичная раскладка или меняется со временем; урон в секунду.
- Управление: WASD + мышь (как в Zombie Arena), переключение режима клавишами 1/2 или Q.

## Архитектура игры под RL (главное требование)
В Zombie Arena вся логика сидит в `main()` вперемешку с отрисовкой, вводом и `sf::Clock`. Для RL так нельзя:
- **Симуляция отдельно от отрисовки.** Класс `World` не знает про окно и клавиатуру:
  - `reset(seed)` начинает новый эпизод;
  - `step(const Action&)` продвигает игру на один шаг и возвращает награду и признак конца эпизода;
  - отдельный метод выдаёт наблюдение.
- Отрисовка SFML только читает состояние `World`. Режимы запуска:
  - human — игрок управляет с клавиатуры и мыши;
  - headless — без окна, для обучения;
  - replay — показывает игру агента в окне.
- **Фиксированный шаг** dt = 1/60 с вместо реального времени. Время прохождения = число шагов, и обучение идёт намного быстрее реального времени.
- **Детерминизм**: единственный `std::mt19937` внутри `World`, инициализированный из `seed`. Никаких `srand(time(0))` (в Zombie Arena это было в `Zombie::spawn`).
- Из оригинала не переносить баг `Zombie::update`: там `if (playerX > m_Position.y)` вместо `m_Position.x`.

## План RL-части
- **Связка C++ → Python** через pybind11, обёртка — среда Gymnasium (`reset`/`step`).
- **Наблюдение** — вектор признаков, не пиксели:
  - позиция, HP и режим игрока;
  - HP босса и фаза его атаки;
  - относительные позиции и скорости K = 8 ближайших снарядов;
  - щупальце: фаза, таймер, края полосы относительно игрока;
  - окно 7×7 клеток вокруг игрока (тёмная / светлая / за краем) вместо полной карты 32×12;
  - доля прошедшего времени эпизода (из-за лимита maxSteps).
- **Действия дискретные**: движение (8 направлений + стоять), прицел (например, 16 направлений), режим стрельба/щит, стрелять/не стрелять. Возможно, удобнее `MultiDiscrete`.
- **Награда**, которую предстоит настраивать:

$$r_t = -c_{\text{time}} + c_{\text{hit}}\cdot \text{dmg\_to\_boss}_t - c_{\text{dmg}}\cdot \text{dmg\_taken}_t + R_{\text{win}}\cdot \mathbb{1}[\text{boss killed}] - R_{\text{death}}\cdot \mathbb{1}[\text{player dead}]$$

- **Бейзлайны**: случайный агент и простой скриптовый бот. Скриптовый бот даёт эталонное время прохождения.
- **Обучение**:
  1. сначала PPO из Stable-Baselines3 — проверить, что среда обучаема;
  2. потом своя реализация PPO по мотивам Моралеса и сравнение с SB3.
- Curriculum: начинать с урезанного босса (меньше HP, одна атака) и усложнять.
- Обучение идёт на CPU MacBook; для векторного наблюдения этого достаточно.

## План на 5 недель (дедлайн — 1 декабря 2026)
Полную версию нужно сделать за 5 недель, начиная с 28 октября 2026. Для этого нужно примерно **25–30 часов в неделю**.

«Полная версия» означает:
- игра;
- среда Gymnasium;
- бейзлайны;
- PPO из SB3;
- **своя реализация PPO**;
- оценка агента и replay.

| Неделя | Даты | Что делаем | Результат к концу недели |
|---|---|---|---|
| 1 | 28 окт – 3 ноя | **День 1:** зафиксировать числа баланса (закрыть открытые вопросы, можно грубо). **Дальше:** `World` + рендер SFML, ручная игра. Сначала снаряды + тёмные клетки + щит, щупальце — в конце недели | В игру можно играть вручную, босса можно убить |
| 2 | 4 – 10 ноя | Headless-режим, тест детерминизма (один seed → одинаковый эпизод), замер шагов/с, pybind11 + среда Gymnasium, случайный и скриптовый бейзлайны, пробный запуск PPO из SB3 | `env.step()` работает из Python, есть эталонное время скриптового бота |
| 3 | 11 – 17 ноя | Награда + PPO из SB3 до первой победы; curriculum (урезанный босс → полный). Параллельно начать свою PPO и отладить её на CartPole | Агент SB3 убивает босса; своя PPO решает CartPole |
| 4 | 18 – 24 ноя | Своя PPO на игре; обучение до уровня, сравнимого с SB3 | Своя PPO убивает босса |
| 5 | 25 ноя – 1 дек | Финальные запуски (3 сида), сравнение со случайным агентом, скриптовым ботом и SB3; replay лучшего эпизода в окне. **Половина недели — запас** на отставание | Готовый проект |

Самые рискованные недели — 3 и 4: агент может долго не учиться.

**Правила, чтобы уложиться:**
- **Таймбокс на игру — строго 1 неделя.** Если не успеваем, щупальце становится второй стадией curriculum (добавляется в неделю 3), а не блокирует старт RL.
- **Алгоритм для своей реализации — только PPO**, без DQN. PPO лучше подходит к этой задаче, а SB3 PPO служит эталоном при отладке.
- **Своя PPO сначала проверяется на CartPole.** Так ошибки алгоритма не смешиваются с ошибками среды.
- **Подбор гиперпараметров ограничен по времени.** Если за 2 дня после первой победы нет улучшения, берём то, что есть.
- **Обучение запускать на ночь** (`caffeinate -i`), днём писать код.
- Если к концу недели 2 среда не готова, ментор сразу предлагает, что ещё урезать в игре.
